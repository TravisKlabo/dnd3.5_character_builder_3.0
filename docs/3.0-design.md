# D&D 3.5 Character Builder 3.0

## Direction

Preserve the familiar 2.0 player-sheet layout and existing character-management
features while reducing startup work, repeated computations, and maintenance risk.
The original 2.0 repository remains separate and unchanged.

Targets remain the browser and Electron, with Windows NSIS and Linux
AppImage/Debian packaging configurations. Application printing and PDF generation
are deliberately excluded from 3.0.

## Architecture

- `src/App.tsx`: character lifecycle and screen orchestration.
- `src/components/`: creation, character, equipment, store, forge, crafting, spell
  screens, shared panels, and pickers.
- `src/domain.ts`: typed character/content definitions and foundational rules.
- `src/rules.ts`: reusable character, progression, combat, and equipment rules.
- `src/data/`: character/equipment catalogs, spell progression, and lazy spell loading.
- `src/storage.ts` and `src/validation.ts`: validated local persistence and import boundaries.
- `tests/`: focused rule and UI regression tests.

Secondary screens use lazy imports. Spell data is deferred until needed and indexed
after loading. Equipment lookups use a revision-aware index; successful custom-item
changes invalidate it and notify the store. There are no new runtime dependencies.

## Character lifecycle

```text
New character -> Creation draft -> Finalized character
                                      |
                                      v
                                 Level-up draft
                                  /        \
                              Cancel      Validate choices
                                |              |
                         Discard draft     Roll hit points
                                               |
                                           Confirm level
```

Level-up drafts deep-copy the original character. Cancel discards the draft;
confirmation applies proposed data only after validation. Hit points continue to
be rolled before confirmation, matching the actual 2.0 implementation rather than
the older design document's proposed post-commit roll.

## Reliability boundaries

- Character imports validate identity, ability scores, supported classes, levels,
  selections, inventory, optional spell tracking, and custom items.
- Corrupt saved data is reported and is not automatically overwritten.
- Storage failures do not produce a success notification.
- Custom catalog persistence must succeed before the live catalog changes.
- Lazy content failures show an error/retry; screen failures are logged and leave
  Save/Export accessible.
- JSON exports remain the portable character transfer format.

## Retained product goals

- Calculate derived statistics rather than independently editing them.
- Keep finalized character data separate from a provisional level-up.
- Support core D&D 3.5 and optional authorized Dragonlance content.
- Keep source attribution and avoid presenting ambiguous rules as verified facts.
- Use open/licensed content or authorized user-provided data.

## Still unfinished

These are inherited goals, not claims of implemented 3.0 functionality:

- A complete, independent rules registry with consistent verification metadata.
- Structured validation categories for errors, warnings, house rules, and
  unverified content.
- Full correctness/source verification of all core and Dragonlance mechanics.
- Campaign-configurable house rules and hit-point policies.
- Platform-specific installer/runtime verification on Windows and Linux.

The initial combat correctness pass replaces several inherited attack/damage
formulas with SRD-derived expected results. Both sheets pass weapon slot context
to the shared calculator, so off-hand damage and thrown attacks are not inferred
from the weapon name alone. The store also uses the shared equip helper, including
normalized weapon traits and two-handed/off-hand weapon conflicts. Non-light one-handed
weapons may occupy the off hand with the corresponding higher attack penalties.
Small-size metadata for core halflings and gnomes is now explicit.

These are intentional behavior corrections, not merely refactoring. The
[README rules section](../README.md#rules-and-scope) lists verified cases, SRD
references, and remaining limitations. Broader spellcasting and Dragonlance
verification remain unfinished.

## Performance checks

Production builds enforce a 430,000-byte initial JavaScript budget, below the
approximately 611,000-byte 2.0 baseline. A repeatable equipment benchmark requires
equivalent lookup results and a minimum 2x improvement over repeated sorting.
These checks do not imply that every device, screen, or interaction is optimized
to a theoretical maximum.

## Class-specific spellcasting

The lazy spell screen renders one active class sheet behind accessible subtabs,
instead of stacking every caster's sheet vertically. Its shared layout delegates
class access, casting ability, daily slots, and known-spell limits to shared rules
helpers. Creation and level-up validation use those same helpers. Wizard spellbook
level-up additions are counted across spell levels rather than independently per
level.

`knownSpellsByClass` and `preparedSpellsByClass` are authoritative when a class
entry exists, including an empty array. Preparation arrays may contain repeated
names to represent multiple copies; the legacy flat arrays remain compatibility
summaries. Legacy unclassified selections are resolved once per spell, not copied
to every class. Edits initialize missing class entries without discarding another
class's selections.

`expendedSpellSlotsByClass` stores class -> spell-level string -> expended slot
indexes. It is optional for old saves, validated on import, and follows the normal
character/draft lifecycle. Tab-local state is limited to navigation and open
pickers; preparation and usage live in the character, survive navigation, and
remain provisional during level-up.

Cleric domains have separate selection, preparation, and expenditure fields rather
than being folded into ordinary slots. Domain spell selections retain their
source domain and are validated on import. Class-skill powers share the skills
rules; other powers and unverified deity associations are explicitly manual.
This is still not a complete casting engine. The
[README](../README.md#class-spell-sheets) documents class behavior, legacy ownership
ambiguity, source references, and remaining casting limitations.

## Wizard spellbook and learning

Wizard sheets now have nested Spellbook / Daily Preparation tabs. The book owns
free spell selection and the learning dialog; preparation never changes the book.
Both views read the same class-scoped character data. Starting and level-up
allowances share `getWizardFreeSpellAllowance` with creation/level-up validation.
Copy requirements (DCs, pages, writing cost/time) use `getWizardCopyRequirements`.
Source rules are linked in the README.

`wizardSpellLearning` is an optional spell-name map of successful learning records:
source, recording timestamp, deciphering method, and entered check totals where
applicable. Acquisition classification still uses `spellAcquisitionByClass`.
The optional records are validated on import and included in ordinary saves and
exports. Old saves need no migration or assumed successful checks. Removing an
externally learned spell removes its record and prepared copies, without touching
another class's copy of the same spell.

Learning dialogs require manual confirmation and actual totals rather than making
automatic rolls. They do not mutate inventory, gold, or time, and do not persist
failed attempts. Research/rewards require DM adjudication rather than invented
fixed costs. Specialization and physical-book management remain separate work.
